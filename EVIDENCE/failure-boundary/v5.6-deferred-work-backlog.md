## V5.6-Y1 — Retry / Resilience Integration

**Status:** READY

**Goal:** Replace standalone retry behavior with canonical `RetryExecutor` from `components/Operations/Resilience/System/Capabilities/Retry/`.

**Current state:**
- Retry attribute is compiled and recognized
- `RetryFailedAction` implements its own retry loop with backoff strategies (none/linear/exponential+jitter)
- Resilience `RetryExecutor` exists at `components/Operations/Resilience/System/Capabilities/Retry/RetryExecutor.php`
- Resilience `RetryOptions` and `RetryResult` exist as value objects
- Standalone retry is functional and well-tested (2 tests: succeeds on 2nd attempt, exhausts after max)

**Blocker:** None. Canonical Resilience RetryExecutor exists.

**Required work:**
1. Modify `RunFailurePipeline` or `RetryFailedAction` to delegate retry execution to `RetryExecutor`
2. Map FailureBoundary `Retry` attribute policy to `RetryOptions`
3. Keep `Retry` attribute as policy declaration only — actual retry execution belongs to Resilience
4. Remove or demote standalone retry engine to internal fallback / deferred
5. Update docs to reflect Resilience dogfooding

**Required tests:**
- Transient failure succeeds after retry (through Resilience RetryExecutor)
- Retry stops after max attempts (through Resilience RetryExecutor)
- Non-retryable failure does not retry (classified failure skips retry)
- Canonical Resilience owner is used (assert RetryExecutor is invoked)
- Standalone retry engine is removed or demoted to internal fallback

**Acceptance criteria:**
- Retry becomes GREEN only when dogfooded through Resilience `RetryExecutor`
- No duplicate retry logic exists outside Resilience
- `Retry` attribute remains a declarative policy, not an execution engine

**Dependencies:** `components/Operations/Resilience/System/Capabilities/Retry/RetryExecutor`

**Risk:** LOW — RetryExecutor exists and is tested. Integration is straightforward mapping.

**Evidence file:** `EVIDENCE/failure-boundary/deferred/V5.6-Y1-retry-resilience.md`

## V5.6-Y2 — DeadLetter / Queue Transport Integration

**Status:** BLOCKED

**Goal:** Replace NDJSON `error_log` fallback transport with canonical Queue/DeadLetter transport.

**Current state:**
- DeadLetter attribute is compiled and recognized
- `SendFailureToDeadLetter` produces a structured envelope (type/version/failure/context/timestamp)
- Transport is `error_log` with NDJSON format — functional but not canonical
- DeadLetterQueue interface exists at `components/SystemDesign/System/Capabilities/Messaging/DeadLetters/DeadLetterQueue.php` (SystemDesign capability, not production transport)
- Queue component exists at `components/Operations/Queue/System/Capabilities/` with MemoryQueue, ArrayQueue, DatabaseQueue drivers
- FailedJobsSchema exists at `components/Operations/Queue/System/Capabilities/Queue/FailedJobs/FailedJobsSchema.php`

**Blocker:** No canonical Queue/DeadLetter transport is wired for FailureBoundary use. SystemDesign DeadLetterQueue is a modeling capability, not a production transport. Operations/Queue has drivers but no explicit dead-letter integration with FailureBoundary.

**Required work:**
1. Define a FailureBoundary-to-Queue dead-letter transport boundary
2. Create a `QueueDeadLetterTransport` or similar that bridges FailureBoundary envelope to Queue/FailedJobs
3. Map `DeadLetter` attribute policy to queue payload serialization
4. Ensure sensitive context is redacted before queue transport
5. Define dead-letter transport failure behavior (what happens if queue is down?)
6. NDJSON `error_log` fallback becomes fallback-only or is removed
7. Update docs to reflect Queue dogfooding

**Required tests:**
- Exhausted failure sends to canonical dead-letter owner
- Payload/failure context is safely serialized
- Sensitive context is redacted before transport
- Dead-letter transport failure behavior is defined and tested
- NDJSON fallback is either removed or documented as fallback-only

**Acceptance criteria:**
- DeadLetter becomes GREEN only when canonical Queue/DeadLetter is used
- Structured envelope is preserved through transport
- Transport failure does not swallow original failure

**Dependencies:** Canonical Queue/DeadLetter transport wired to FailureBoundary. Either `components/Operations/Queue` dead-letter integration or a new `FailureBoundaryDeadLetterQueue` capability.

**Risk:** MEDIUM — Requires design decision on which Queue component owns dead-letter transport. SystemDesign DeadLetterQueue is modeling, not transport. Operations/Queue has drivers but needs dead-letter integration.

## V5.6-Y4 — Timeout Enforcement

**Status:** DEFERRED

**Goal:** Decide and implement Timeout only when runtime support exists.

**Current state:**
- `Timeout` attribute exists at `framework/System/Capabilities/FailureBoundary/Foundation/Attributes/Timeout.php`
- Attribute is compiled but NOT enforced
- No timeout enforcement exists in `RunProtectedAction` or `RunFailurePipeline`
- No fiber/async runtime timeout support in current codebase
- V4-17 Optional Runtime Adapters proved ReactPhpAdapter but fiber-level timeout not implemented

**Blocker:** No fiber/async runtime timeout enforcement available. Timeout requires:
- Fiber-based execution with timeout
- pcntl_alarm process boundary
- Runtime adapter timeout support
- Or equivalent mechanism

**Required design decision:**
- Should Timeout be part of FailureBoundary or part of Resilience (Resilience already has `Timeout.php`)?
- If Resilience owns timeout, FailureBoundary `Timeout` attribute maps to Resilience timeout policy
- If FailureBoundary owns timeout, it needs its own enforcement mechanism

**Required tests (when implemented):**
- Operation exceeding timeout fails with timeout-specific response
- Operation under timeout succeeds normally
- Timeout is reported through ReportFailure pipeline
- Cleanup runs after timeout
- Timeout does not corrupt request/worker state

**Acceptance criteria:**
- Timeout remains DEFERRED_NOT_ENFORCED until real enforcement exists
- Must not claim production GREEN until actual enforcement exists
- If Resilience owns timeout, FailureBoundary Timeout attribute must delegate to Resilience

**Dependencies:** Fiber/async runtime support OR Resilience Timeout integration

**Risk:** MEDIUM — Timeout implementation in PHP without proper runtime support can corrupt worker state. Must not implement naive `sleep()` or `set_time_limit()` approach.

**Evidence file:** `EVIDENCE/failure-boundary/deferred/V5.6-Y4-timeout-enforcement.md`

## V5.6-Y5 — RecoverWith Enforcement

**Status:** DEFERRED

**Goal:** Define recovery strategy interface and enforce RecoverWith behavior.

**Current state:**
- `RecoverWith` attribute exists at `framework/System/Capabilities/FailureBoundary/Foundation/Attributes/RecoverWith.php`
- Attribute is compiled but NOT enforced
- No recovery handler contract exists
- No dependency resolution boundary for recovery handlers
- No failure context passing mechanism
- No recovery result mapping
- No recovery failure behavior definition

**Blocker:** No recovery strategy contract exists. RecoverWith requires:
- Recovery handler interface/contract
- Dependency resolution (how is recovery handler instantiated?)
- Failure context passed safely to recovery handler
- Recovery result mapping (what does recovery return?)
- Recovery failure behavior (what if recovery itself fails?)

**Required design:**
1. Define `RecoveryHandler` interface with `recover(FailureContext): RecoveryResult`
2. Define dependency resolution boundary — DI container, factory, or composition root?
3. Define failure context safety — what context is safe to pass to recovery?
4. Define recovery result mapping — how does recovery result become HTTP response or rethrow?
5. Define recovery failure behavior — fallback to rethrow? secondary recovery?

**Required tests (when implemented):**
- Recovery handler is invoked when failure matches RecoverWith policy
- Recovery result is returned to caller
- Recovery failure falls back/rethrows correctly
- Original failure is preserved in context

**Acceptance criteria:**
- RecoverWith remains DEFERRED_NOT_ENFORCED until runtime behavior exists
- Must not compile-only claim production readiness

**Dependencies:** Recovery handler contract, dependency resolution boundary

**Risk:** MEDIUM — Recovery handlers can introduce hidden dependencies, circular recovery loops, or silent failure swallowing. Must design carefully.

**Evidence file:** `EVIDENCE/failure-boundary/deferred/V5.6-Y5-recoverwith-enforcement.md`
