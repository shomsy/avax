## PHASE 0: Context and Scope Gate

### 0.1 System Identity

- **System Type:** framework tooling / benchmark infrastructure
- **Primary Consumers:** developers, CI pipeline, governance validation
- **Runtime Context:** CLI benchmark execution, in-process measurement
- **Lifecycle:** stable core — V5.5 benchmark infrastructure

### 0.2 Intended Use-Cases and Anti-Use-Cases

- **Intended Use-Cases:**
  - Measure AvaX framework performance across 13 benchmark stages
  - Produce JSON evidence files for governance validation
  - Compare AvaX performance against baselines (PSR-15, other frameworks)
- **Anti-Use-Cases:**
  - Not a production runtime component
  - Not a replacement for external APM/profiling tools
  - Not a load testing tool for production systems

### 0.3 Non-Goals

- Real-time production monitoring
- External service benchmarking (Redis, PostgreSQL)
- Browser-based performance testing
- Distributed system benchmarking

### 0.4 Compatibility Contract

- **Public API Stability Requirement:** moderate — internal benchmark API, may evolve
- **Backwards Compatibility:** optional — JSON evidence format should remain stable
- **Performance Budget:** benchmarks must not add overhead to the code being measured

## ARCHITECTURE NOTES

### 1.1 Actual Execution Flow (As-Built)

```
v5_5_benchmark_runner.php (CLI entry)
  -> RunBenchmark::run(name, callable, iterations, warmup)
    -> warmup loop
    -> measurement loop (microtime timing)
    -> BenchmarkResult::fromTimes(sortedTimes, memory stats)
  -> writeEvidence(name, results, stage, evidenceDir)
    -> BenchmarkResult::toArray()
    -> file_put_contents(EVIDENCE/v5.5/{name}.json)
```

**This is how the system actually works:**
The benchmark runner is a CLI script that instantiates `RunBenchmark`, executes benchmark workloads (including real `Avax::create()` app creation and `RuntimeRequest` handling), measures timing via `microtime(true)`, aggregates results into `BenchmarkResult` objects, and writes JSON evidence files to `EVIDENCE/v5.5/`.

### 2.1 Primary Axis

> "This system is fundamentally organized around **measurement**."

BenchmarkResult holds measured data. RunBenchmark performs measurement. The script orchestrates measurement stages.

### 2.2 Secondary Axis

> "Secondary axis: **evidence generation** (JSON output, environment capture, stage tagging)."

This adds mild complexity but is necessary for governance compliance.

### 3. Central Abstraction Stress Test

- Does every feature flow through it? **Yes** — all benchmarks use BenchmarkResult
- Does it accumulate responsibilities over time? **No** — BenchmarkResult is a pure data holder
- Is it harder to change than surrounding components? **No** — it's a simple readonly class

**Assessment: Pass**

### 4. Responsibility and Boundary Mapping

| Component | Orchestrates | Executes | Holds State | Notes |
|-----------|-------------|----------|-------------|-------|
| v5_5_benchmark_runner.php | Yes — stage orchestration | No — delegates to RunBenchmark | No — stateless | CLI entry point, all stages |
| RunBenchmark | No | Yes — runs benchmark loops | No — per-call only | Core measurement engine |
| MicroBenchmarkRunner | Yes — predefined micro workloads | No — delegates to RunBenchmark | No | Convenience wrapper |
| BenchmarkResult | No | No | Yes — readonly data | Pure data holder |
| BenchmarkSuite | No | No | Yes — readonly data | Aggregation holder |

**Responsibility boundaries are: clear.**

### 5. Pipeline and Control Flow Analysis

The benchmark script runs stages sequentially (V5.5-01 through V5.5-12, skipping V5.5-05). Each stage is independent. No shared mutable state between stages.

**Is this pipeline a formal state machine? No.**
**Foundational Risk: Implicit ordering** — stages are hardcoded in sequence. Acceptable for a benchmark script.

### 6. Mutability Audit

| Object | Scope | Lifetime | Why Mutable? | Classification |
|--------|-------|----------|--------------|----------------|
| $results array (script) | Script | Per invocation | Accumulate results | Necessary |

| BenchmarkResult | Object | Immutable (readonly) | N/A | Necessary |

**Mutability is: justified.**

### 7. System Invariants

| Invariant | Enforced Where | Status |
|-----------|---------------|--------|

## GOVERNANCE FINDINGS

### Governance Finding: Missing benchmark unit tests

- **Governance Source:** `how-to-unit-test.md` -> behavior-first tests, happy/failure/edge
- **Required Rule:** Tests must cover happy path, failure path, and edge cases
- **Observed Gap:** No dedicated unit tests for `BenchmarkResult::fromTimes()`, `BenchmarkResult::toArray()`, `BenchmarkResult::toCanonicalFormat()`, or `RunBenchmark::run()` beyond the existing V4BenchmarksTest which covers basic functionality
- **Where It Fails:** No tests for zero-iterations, all-errors, large iteration counts, or malformed inputs
- **Why It Matters:** Benchmark infrastructure produces evidence that drives governance decisions. If the measurement tool is wrong, all downstream decisions are wrong
- **Required Action:** test
- **Suggested Fix:** Add `tests/Unit/Framework/Benchmarks/BenchmarkResultTest.php` and `tests/Unit/Framework/Benchmarks/RunBenchmarkTest.php` covering: zero iterations (empty times array), all errors, single iteration, large percentile arrays, status classification logic
- **Severity:** Medium

## FINDINGS

### Finding: V5.5-05 stage missing from benchmark runner

- **Symptom:** The `v5_5_benchmark_runner.php` script handles stages V5.5-01 through V5.5-04, then skips to V5.5-06. No code path for V5.5-05 Reference App Benchmarks.
- **Root Cause:** V5.5-05 requires loading individual `examples/v4/*` apps as benchmark targets, which was not implemented.
- **Impact:** V5.5-05 cannot produce evidence. Stage remains YELLOW.
- **Evidence:** `tooling/benchmarks/v5_5_benchmark_runner.php` lines 68-80 (jumps from V5.5-04 to V5.5-06)
- **Risk Level:** Medium

### Finding: Benchmark closures in script use non-static anonymous functions

- **Symptom:** The benchmark runner script uses `fn() => ...` closures that capture `$runner`, `$results`, etc. These are not declared `static`.
- **Root Cause:** Closures need access to local variables. Making them static would require passing dependencies explicitly.
- **Impact:** Negligible — this is a CLI script, not a hot path. Non-static closures in scripts are acceptable.
- **Evidence:** `tooling/benchmarks/v5_5_benchmark_runner.php` — multiple `fn()` usages
- **Risk Level:** Low

### Finding: Memory measurements show consistent values across benchmarks (verified authentic)

- **Symptom:** All JSON evidence files show `memory_before_bytes: 10485760` (10MB) and `memory_peak_bytes: 13107200` (12.5MB) — identical across microbenchmarks.
- **Root Cause:** PHP's `memory_get_usage(true)` reports real OS-level memory allocation, which uses block-based allocation. Micro-operations like `array_map`, `new stdClass()`, and `hash()` do not trigger new OS-level allocations. The 10MB base is PHP's initial real memory allocation with opcache enabled.
- **Impact:** None — values are authentic. Re-running `php tooling/benchmarks/v5_5_benchmark_runner.php V5.5-02` produced identical memory values, confirming they are real measurements.
- **Evidence:** `EVIDENCE/v5.5/microbenchmark-results.json` — verified by re-run
- **Risk Level:** None (false positive finding)

## DECISION

**Keep and Improve**

The benchmark infrastructure is fundamentally sound. The measurement engine (`RunBenchmark`, `BenchmarkResult`) is well-designed with proper warmup, error counting, percentile calculation, and memory tracking. The data model is immutable (readonly) and follows PHP 8.x conventions.

The primary issues are:
1. V5.5-05 is not implemented (stage gap, not design flaw)
2. No dedicated unit tests for benchmark infrastructure (test coverage gap)
3. Missing how-this-works.md documentation (documentation gap)

These are fixable without redesign. Memory values were verified as authentic by re-running benchmarks.
