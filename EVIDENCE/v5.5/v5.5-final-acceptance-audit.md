## V5.5-05 Detailed Analysis

### What V5.5-05 Requires

Reference App Benchmarks — run the 13 reference applications in `examples/v4/` through benchmark scenarios, producing evidence of their performance characteristics.

### Current State

1. **13 reference apps exist** in `examples/v4/`: hello-world, secure-registration-api, url-shortener, parking-lot, webhook-receiver, queue-worker-demo, outbox-messaging-demo, file-upload-storage-demo, observability-demo, feature-flag-demo, service-to-service-demo, runtime-doctor-demo, system-design-report-demo
2. **No evidence file** `reference-app-benchmarks.md` or `reference-app-benchmarks.json` exists
3. **No CLI command** `benchmark:reference-apps` exists
4. **Benchmark runner** (`v5_5_benchmark_runner.php`) does not include V5.5-05 — it jumps from V5.5-04 to V5.5-06

### Why V5.5-05 Is Not Runnable

The reference apps in `examples/v4/` are structured as standalone PHP files that each create their own `Avax::create()` application and run it. They are not designed as reusable benchmark workloads. Each app would need:
- A CLI entry point that loads the app
- A benchmark scenario definition
- A result writer

This is not trivial scaffolding. It is real implementation work.

### Overlap with V5.5-03/V5.5-04

V5.5-03 (Runtime Benchmarks) and V5.5-04 (HTTP Throughput) already benchmark the same patterns:
- App creation + route registration (V5.5-03: `app_creation`)
- Single request handling (V5.5-03: `single_request`, `param_request`)
- Hello endpoint throughput (V5.5-04: `hello_throughput`)
- JSON API throughput (V5.5-04: `json_api_throughput`)
- Parameter routing throughput (V5.5-04: `param_throughput`)

The reference apps would test the same patterns but with more realistic routing, validation, and response complexity. The delta is "real app complexity" vs "synthetic benchmark patterns."

### Decision

**V5.5-05 remains YELLOW.** The blocker is:

- Reference apps exist but are not independently CLI-benchmarkable
- Creating a CLI benchmark harness for each app is implementation work, not evidence collection
- V5.5-03 and V5.5-04 already cover the core HTTP performance patterns
- The delta (real app complexity benchmarking) is valuable but not critical for V5.5 acceptance

**Owner:** V5.6 or separate V5.5-05 closure pass
**Next action:** Create `benchmark:reference-apps` CLI command that loads each example/v4/ app, runs a representative benchmark scenario, and writes `reference-app-benchmarks.json`

## phpstan.neon Ignore Rule Audit

### Rule Under Review

```yaml
- message: '#Call to .* on a separate line has no effect#'
  path: 'framework/System/Capabilities/Benchmarks/MicroBenchmarkRunner.php'
```

### Classification: JUSTIFIED_BENCHMARK_SIDE_EFFECT

### Reason

The `MicroBenchmarkRunner` class runs benchmark closures that intentionally discard their return values. The purpose is to measure the cost of the operation, not to use its result. Examples:

- `array_map(static fn ($v) => $v * 2, range(1, 100))` — measures array_map cost
- `new stdClass()` — measures object creation cost
- `'hello' . ' ' . 'world'` — measures string concat cost
- `json_decode(json_encode(...), true)` — measures JSON roundtrip cost

PHPStan correctly identifies these as "no effect" because the return values are not used. This is intentional for benchmarking.

### Scope Assessment

- The ignore rule is scoped to **one file**: `MicroBenchmarkRunner.php`
- It does **not** suppress "no effect" warnings globally
- It does **not** hide unrelated warnings
- The narrow scope means it cannot mask issues in other code

### Risk: LOW

This is a standard benchmark pattern. Suppressing this warning for the benchmark file is correct.

### Alternative Considered

Could wrap results in a discard function like `benchmark_discard($result)` — but this adds function call overhead to the measurement itself, defeating the benchmark purpose.
